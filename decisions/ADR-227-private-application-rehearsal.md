# ADR-227: Real application rehearsal on the restored owner snapshot

Date: 2026-10-27

Status: Design accepted by Lead, Platform and independent reviewer. Bounded
source implementation authorized below; no actual-run grant.

## Purpose and first deliverable

ADR226 proves recovery of the fixed actual schema9 snapshot. ADR225 still
requires combined application/browser/provider and concurrent crawler/user checks
before live hierarchy activation. Keep that full gate intact. The first bounded
implementation here proves real schema17 application HTTP/database behaviour;
it must explicitly report browser, E5, provider and production-capacity checks as
unfinished. No invented model or provider response may stand in for those gates.

Reuse the maintained owned native fixture and complete authenticated restore,
all19 fingerprint checks, existing25-record restoration ledger and33 phases.
Do not copy a controller, fork a numbered experiment, invoke the fixed live55432
operator, change the live database, or stop the original crawler.

After verified restore and before retiring A, run the existing owner installer
on the same owned database with explicit head0/policy0 CAS and default depth1.
Require exact schema17, fixed installed numeric matcher and owner policy. Verify
all18 original non-migration table fingerprints remain unchanged immediately
after installation. The migration table must instead match all17 fixed hashes.
Preserve original IDs, source links, discussions, contributions, revisions and
receipts. This is a real full-data upgrade check, not another empty fixture.

## Real private application composition

Use `openDormantPostgresApplication` with real issued app-role adapters, a
distinct URL-selection connection, hierarchy enabled and no worker database.
Use `createLoopbackServer` for real HTTP on one fixed isolated loopback port;
preserve canonical Host, origin, pairing and session checks. Never send a
request to live4174 or fall back there. Keep fixed test pairing capability and
private realm separate from the production capability and account stores.

Private local account/conversation files live inside the owned cluster leaf,
under inherited owner/SYSTEM ACLs and the existing6GiB tree limit. They never
replace or copy production stores. Seed explicit private test accounts using
the real account repository/service's existing fixture-email mechanism and one
new private HMAC key, then reopen the unchanged production application with
normal session validation. This tests session/write handling, not real external
identity verification. No copied live sessions, fake ChatGPT identity, provider
credentials or external email are needed for this stage.

Exercise exact-profile startup, health, independent Search Topics metadata,
saved-page discussion reads, authenticated human posting/reply/edit/delete,
invalid-origin/Host/session refusals, policy-refresh behaviour and bounded
concurrent HTTP reads from the private seeded actors. Retain finite case names,
status/count/timing summaries only. Keep actual comments, session tokens, HMAC
keys, SQL and raw errors out of reports. Additional private test writes are
distinguished from the original backed-up contributions.

Use only original issued connections. Budget: admin + A owner + restore backend
+ app + URL reader + B owner =6 lifetime connections; at most two further
explicitly reviewed role connections remain. A serialized two-connection HTTP
rehearsal does not prove the production42-pool maximum or many-user capacity.
Do not start `openInstalledHierarchyRuntime`, which immediately starts claims
and existing-page preparation and allocates E5, in this first stage.

Close server, sockets, application/local stores and app connections before
retiring A and empty B. Observe all original async work; timeouts do not prove
settlement. Preserve private CPU300, memory1GiB, Node64MiB, processes32,
callback clamp and overall360/380/390 epochs. If the combined work cannot fit,
record the actual failure; no automatic increase or substitute small dataset.

The private HTTP mode needs a closed fixed entry and an additional bounded
application proof, required by its supervisor. The normal restore entry remains
unchanged. Its original restoration ledger stays25/3; application cases are
separate, explicitly named and counted. Neither an absent application proof nor
an invented response can produce a successful application rehearsal.

## Remaining combined gate

After HTTP/database evidence, connect the existing contained Chrome harness to
the actual owned endpoint. It may fulfill intercepted allowed API requests with
the real private HTTP response; it may not continue to live4174 or pretend its
existing invented responses are backend evidence. Browser-owned profiles,
screenshots and reports remain private. Review the lifetime/handshake separately.

Real E5 placement needs an explicit resource plan: prior standalone RSS was
about877MB, so it is not established to fit beside PostgreSQL inside1GiB. Prefer
reusing one owned encoder across worker/crawler rather than duplicating loaded
models. Measure and verify original output compatibility before changing their
production composition. Validate retained legacy queue material, real worker
ingestion, existing-page preparation, dashboard updates and foreground latency
under crawler/user contention. Preserve IDs, digests, deadlines and saved crawler
progress; never reset queues to obtain a passing test.

Actual provider testing must use a separately reviewed existing-session path
without copying live stores or competing refresh writers. User authorization to
make AI posts persists, but source/lifetime/privacy controls still apply. These
remaining checks, broader fine-topic coverage and final seal/cutover are not
waived by the first HTTP/database stage.

## Source implementation grant

Platform owns new `portable/integration/private-application-rehearsal.js` and
its focused test. Maintained owns the small internal after-verification extension
in `owner-restore-native-check.js` and its test, plus one thin fixed HTTP entry
and test. Lead owns the maintained driver/test's closed HTTP mode, required
application-proof validator, source catalog and integration. Keep the normal
restore entry unchanged; no public real callback/connection selector is added.

The hook runs only after all original schema9/data checks and complete restore
result have passed. Await it under the original callback. Require exact17 and18
unchanged non-migration table fingerprints before HTTP writes or policy changes.
Adapt each issued app/URL client with a bounded serial transaction queue; no
hidden pool, DPAPI provider or live55432 fallback. Seed usernames and sessions,
then close the bootstrap account repository before normal reopening. Leave
`chatgptFetchImpl` undefined and `ai` absent, so no provider stores open. Assert
normal external login/email-code mechanisms are unavailable at this stage.

Include denial of a second actor editing/deleting the first actor's post,
revoked/forged sessions, `x-demo-actor`, reserved bot usernames and invalid
Host/origin. Topic context may legitimately remain pending; test canonical
fallback without inventing classification proof. Stop admission and settle all
original requests/transactions before application/store/client and A/B closure.
The HTTP mode requires its own bounded closed application proof in addition to
the original successful restoration proof and33 phases; absent/failed proof
cannot pass. Report both the actual4185 destination and canonical4174 Host
validation domain, not production endpoint execution.

Only source edits, pure tests and review are granted. No HTTP listener, database,
encoder/model run, browser, provider request, live migration, queue change or
activation is granted here. Review final source, bindings and fresh resource
admission before a separate one-attempt actual decision.
