### Next real integration slice after quality acceptance

Independent architecture review narrows the first useful slice to a protected
publication resolver plus a full-topology scoped admission boundary. A request
may name an allowlisted publication ID, but cannot supply its trust anchor,
acceptance record, arbitrary file paths or acceptance booleans. The protected
record must bind a genuinely accepted selection and independent quality review
to exact source, selected-artifact, result and policy identities. Compiler
validity alone is not quality acceptance; the failed ADR212 attempt supplies no
such record.

The publication verifier must own the same actual190/196 compile context,
complete canonical topology and207 template. Its server facade privately issues
the207 jobs for that publication; an authentic foreign job with matching-looking
hashes is still insufficient. Root-model JSON, root policy, local-detail artifact,
local builder, paired representation, encoder and native producer-profile hashes
need explicitly named identity domains, not reassignment to the old five generic
publication fields. Publication revision/revocation and current Source/generation
must be rechecked in the admission transaction. Principal authority and current
native document/rights proofs remain separate checks, not properties conferred
by a cached publication capability.

The pure chain already exists in
`apps/local-service/src/application/experimental/`: native-scoped-preparation-v1
prepares the actual observation, native-owner-grouping-v1 separates semantic
support from the owner's selected prefix, and native-canonical-mapping-v1
checks exact topology, field, vector-bit and canonical-material commitments.
The mapper deliberately returns `publicationVerified:false`,
`publicationIdentityChecked:false` and `registryArtifactHash:null`.
These are not flags that an adapter may simply turn on.

A small unregistered SOURCE facade can be tested before real quality acceptance,
using invented accepted-record fixtures and an empty real acceptance registry.
It would accept only a publication ID and ordinary observation/grouping/mapping
inputs, never externally prepared jobs or caller-selected paths and trust anchors.
Trusted construction would own bounded readers and independently fixed record
pins; opening a publication would authenticate the record and candidate bundle
before compiling the actual196 context once. Preparing an observation would
internally call190,196 and207 in order, enforce the same private context, recheck
publication incarnation/revision/revocation before and after, and privately tag
the resulting job. It would not enqueue, register or activate anything. An empty
registry must fail closed. ADR219 separately grants this unregistered SOURCE
implementation after complete architecture review; it supplies no real quality
acceptance.

196 has no context-description accessor. A verifier can compile an internal
depth8/no-override grouping policy and use its actual description to bind the
topology and semantic-transfer identities, then inspect the actual190 observation
description before grouping it in that same context. It must not accept a foreign
authentic job merely because its descriptive hashes match. Root-model JSON hash,
canonical numerical detail-artifact hash and bundle FILE hash are distinct
domains; the old five declared publication fields remain declared claims, not
aliases for these native identities. Protected record issuance needs independent
quality acceptance, not just successful parsing or compilation. A separate
architecture review is required before implementing this proposed facade.

The next implementation needs an authenticated publication and an opt-in,
full-topology scoped canonical lane. The existing experimental
`apps/local-service/portable/canonical-v4/experimental/hierarchy-scoped-ingestion-v1` accepts five
caller-declared publication hashes and flat node IDs; its nodes have no parent
or depth and its feed matches an exact node. It cannot honestly consume the
hierarchical mapper by flattening the tree or truncating it to128 nodes.

1. Verify the selected artifact and complete injective native-to-canonical tree
   against its actual stored publication, revision and revocation state. Bind
   exact builder/encoder/representation/model/policy identities, not merely
   equal-looking hashes. Rejoin authentic mapper jobs to this publication and
   separately trusted current generation, Source incarnation and principal.
2. Build the scoped canonical successor with parent/depth/ancestor closure and
   publication revision. Reuse existing queued-input, lease, replay, addressed
   prior and transaction-finalizer mechanics. Persist the deepest semantically
   supported node, or null for unresolved—not the owner's display prefix.
3. Atomically bind a new canonical root to the same Source version, witness and
   decision while retaining its original topic/discussion destination. Updates,
   policy-depth changes and replay must not move posts or rewind current input.
   Ancestor feeds return bounded, deduplicated canonical IDs and hydrate through
   existing visibility/erasure-aware reads. Shadow hierarchy tests are mechanics
   oracles, not a source of canonical authority.
4. Add a separately versioned native depth policy bound to the published tree,
   using existing owner authentication and revision checks. Do not reinterpret
   the current Ridge `defaultSpecificity:0..100`/`spaceId` settings as native
   `defaultMaxDepth:1..8`/`nodeId` settings. Show inherited versus explicit branch
   overrides and the actual topic path through approved owner/admin access.

Implementation must prove swapped/unpublished/revoked publication rejection,
exact vector bits including negative zero, Source delete/recreate and input
replay safety, stable original root/reply routing, scoped ancestor pagination,
erasure and session/revision races. Then measure the existing200ms p95 targets
below with concurrent readers and the crawler. Separate classifier time, queue
time, extraction, embedding startup, canonical commit and rendered UI time.

remain separately reviewed steps; existing migrations and discussions stay intact.

## First technical milestone E5 matching at different depths

Start with [E5 matching across broad and specific topics](E5_HIERARCHICAL_MATCHING_PLAN.md).
It addresses the main uncertainty before migration or UI work: whether the existing
page vector supports broad membership, child discrimination and an honest stop at
the deepest justified ancestor. It specifies several examples per topic, explicit
parent-stop/outside examples, optional small classifiers on frozen E5 features,
independent calibration and a locked quality/coverage evaluation. Dimensionality
reduction and nested cosine cuts alone do not establish semantic hierarchy.

## Intended product behaviour

Assign each page to the most specific topic supported by reliable evidence, and
make its discussions discoverable through that topic's ancestors. Start with the
existing embeddings and explicit parent–child relationships. Do background work
when pages or topic definitions change, not whenever somebody reads a discussion.

Examples of intended paths are Games → Video games → GTA and Nature → Animals →
Koalas. A general wildlife page may stop at Animals; a page about koala conservation
may reach Koalas. Two pages in different child topics can appear in the same broad
parent view without becoming the same specific discussion.

## Starting point and implementation gap

The current canonical assignment compares a page with fixed Ridge references,
joins qualifying Topic containers and creates a container on a complete no-hit.
It has overlapping membership but no semantic parent–child taxonomy. The active
SQL scan still compares the reference catalog and can take seconds as it grows.

The newer discussion discovery layer builds five nested similarity cuts over
populated public roots. It supports owner-wide and per-base specificity, but is
not a taxonomy of all pages: its labels come from exemplar threads, and its cuts
are not calibrated confidence levels. It does not replace canonical assignment or
prevent empty containers from proliferating. Its current 4,096-root and grouping
work limits cannot simply be carried over to an all-page hierarchy.

Reuse its safe public-card hydration, background-worker lifecycle and owner-policy
guards. Replace its grouping representation deliberately; do not reinterpret its
derived IDs, numeric specificity values or similarity cuts as taxonomy authority.
The frozen PCA/UMAP/HDBSCAN experiment remains an offline result, not the proposed
production assignment engine. See [ADR125](../decisions/ADR-125-owner-controlled-semantic-topic-spaces.md)
and [ADR126](../decisions/ADR-126-exact-related-cache-and-independent-ingestion-admission.md).

## Topic and discussion behaviour

Give each semantic topic a stable ID, a label and aliases, a parent, a short scope
definition, representative examples, and exclusions or confusing alternatives.
Renaming a label never changes identity. For the first version each node has one
parent and the graph is acyclic; a page may separately belong to multiple branches.
Cap depth explicitly rather than forcing every topic into five levels.

Parenthood means an explicit subtopic relationship. Similarity alone must not
make Koalas a child of Australia, or GTA a child of Cars. Related concepts are not
necessarily ancestors. Begin with a small owner-reviewed set of branches and
grow it from reviewed proposals; do not require an exhaustive hand-written taxonomy
of the internet. Proposed labels can use existing titles and extracted terms;
there is no default LLM or provider request for naming or classification.

An approved named topic can exist before it has several crawled pages. Its initial
examples and definition need review; an arbitrary singleton cannot establish a
new shared topic automatically. Automatically proposed branches need independent
support, not duplicate URLs, repeated pages from one publisher or crawler volume.
Keep unresolved pages page-specific and collect bounded proposals in the background.

Each page has one primary assignment and optionally additional independently
confident branch assignments. Ancestors are derived from the accepted paths, not
stored as duplicate page assignments. Do not assign every page to a global catch-all
conversation when no useful branch is supported.

New discussion roots inherit the page's accepted topic by default. Replies remain
in their root's discussion; they are not classified separately from their text.
Changing a page assignment does not move an existing thread or reinterpret its
author's destination. Existing roots receive versioned semantic bindings through
the migration process, while retaining their original canonical IDs and routes.

A parent feed aggregates direct and descendant threads, deduplicated by root ID.
Each card identifies its actual topic, and a breadcrumb lets readers move between
the specific and broad views. A broad parent is not a request to merge all child
threads. Discussions remain one level of reply indentation, as implemented today.

Discover remains global Search Topics; browser navigation does not change its
query or scope. Discussion does not regain related-page suggestions. Selecting a
global topic preview remains read-only and never grants posting or AI authority.

## Confidence and the assignment algorithm

Cosine similarity is a matching signal, not a probability. Define and evaluate a
separate assignment policy with a versioned model, evidence set and calibration.
Do not reuse the existing 0.88 Related threshold, Ridge radius floor, or five
discovery cuts as if they established 88 percent confidence.

1. Reuse the validated embedding for the current Source revision. Begin evaluation
   with the pinned Ridge representation. Compare alternatives only in an explicit
   versioned experiment; never silently switch to raw E5 when Ridge is unavailable.
2. Route coarsely across the active broad branches using several representative
   examples per branch. A single average vector is not a hard gate: a diverse
   parent can be far from a valid child. Evaluate candidate-branch coverage
   separately from the final acceptance decision.
3. Within candidate branches, score child topics against a bounded set of diverse
   examples, including confusing sibling examples and any reviewed exclusions.
   Use absolute match strength, separation from siblings, example support and
   ambiguity. Labels and literal terms may aid retrieval, but do not override
   contradictory semantic evidence or turn an acronym into a confident match.
4. Descend only when the child acceptance rule passes. If two siblings are
   plausible, keep their deepest supported common ancestor. If several branches
   independently pass, preserve those separate paths instead of inventing a common
   semantic parent. Choose the primary path by a deterministic calibrated rule.
5. If no child passes, stop at the supported parent. If no meaningful parent
   passes, return a page-specific unresolved result. Never force the nearest leaf.
6. Record the decision against the exact Source input, hierarchy, examples,
   representation and policy revisions. Return an interpretable reason such as
   accepted child, ambiguous siblings, insufficient evidence or no branch match.

Trusted taxonomy ancestry allows a confident child to inherit its parents; it
does not require the child's vector to pass a second unrelated centroid threshold.
Conversely, confident Games membership alone does not establish GTA membership.
Test both cases explicitly to prevent coarse routing from losing valid leaves.

For example, a page explicitly about GTA gameplay can reach GTA. A page comparing
GTA with several other games may stop at Video games unless the multi-topic rule
is independently satisfied. A page containing the letters GTA in another sense
must not enter that branch. A broad nature page mentioning koalas once should
not be routed as if the whole page were about koalas.

Once accepted, an unchanged page reuses its decision. A later deeper assignment
requires fresh qualifying evidence; avoiding assignment oscillation must never
preserve a revoked example, deleted Source or failed minimum confidence rule.

## Owner control and topic growth

Keep control owner-wide with per-topic overrides, not a personal slider. Separate
three concepts in the policy: the acceptance rule that prevents wrong assignments,
the depth at which broad feeds are presented, and which proposed children are
approved for use. A display setting cannot lower the acceptance rule or manufacture
a narrow assignment. A rare subject may remain a broad view until the owner
approves a useful child; a busy branch may expose more of its existing children.

Collect human participation, independent pages and correction evidence separately
from crawler and AI counts. These signals can propose a refinement, not activate
an automatic split or rewrite history. Review tools should explain why pages would
move, preview affected threads and permit a branch-specific rollback.

The planned dashboard admin login is the eventual management surface. Retain the
existing explicit owner-account gate; do not appoint the first account, infer an
owner from a username, or activate admin privileges while implementing this plan.

## Storage and incremental processing

Add versioned PostgreSQL relations for semantic topic nodes, validated examples,
Source assignment decisions and root-thread semantic bindings. Maintain indexed
ancestor relationships for parent feeds. Keep semantic IDs separate from current
canonical Topic/container IDs so several historical destinations can participate
in one semantic feed without copying or renumbering posts.

Store decision reasons and bounded evidence references, not new copies of captured
page text. The existing Source embedding remains authoritative. Any derived
prototypes need explicit representation hashes, dependency witnesses and a rebuild
or deletion path; they are new derived storage, not permission to retain forgotten
Source vectors indefinitely.

Publish immutable hierarchy revisions atomically. A classifier may commit only if
its Source input, hierarchy and policy witnesses still match. Otherwise mark that
work stale and schedule a current computation; do not overwrite newer decisions.
Use scoped dependencies so changing one branch does not reclassify unrelated
branches, and unchanged visits or new messages do not regroup the page catalog.

Source deletion, forgetting, example revocation, thread withdrawal and account
erasure must immediately invalidate affected public projections and retained
example evidence. Keep roots and all descendants subject to the existing visibility
and deletion policy; no cache may revive removed content while a rebuild runs.

## Fast reads and concurrency

Resolve a saved page by its indexed Source-to-topic decision and load its bounded
feed. Do not load all embeddings, build clusters, run an LLM or regenerate the
hierarchy on an HTTP read. Hydrate displayed messages from fresh canonical rows.
Classify changed/new pages in bounded background jobs with fair admission between
interactive users and crawler work; coalesce identical work and expose real progress.

Initially compare the small broad-node prototype set exactly, then use indexed
parent-to-child lookups and bounded branch work. Do not silently truncate an
oversized branch or claim approximate retrieval found every possible membership.
If candidate retrieval needs approximation later, measure its missed accepted
assignments against an exact reference implementation before activation.

Proposed local acceptance budgets, to be measured under a running crawler:

- Saved page assignment plus first feed: p95 at most 200ms.
- Classification after an embedding is available: p95 at most 200ms of classifier
  work within the evaluated hierarchy bound; queue time is reported separately.
- Parent-topic feed and Search Topics: p95 at most 200ms for a bounded page of results.
- No live read waits for a hierarchy rebuild. Browser extraction/model startup and
  embedding time remain separately measured, not hidden inside classifier numbers.

Benchmark bounded catalog growth, concurrent readers and crawler writes, including
cold startup, queue saturation and branch updates. Publish the actual hierarchy
size, prototype count and memory bounds. These targets are not existing results
or a hosted/million-page performance claim.

The final cutover must remove the exhaustive old canonical assignment scan from
the new-page critical path. Keeping that scan and adding a fast semantic lookup
beside it would not meet the new-page latency objective.

## Implementation sequence and completion gates

### Phase 1 Define and test the decision policy

Create a new taxonomy and classifier module alongside the existing discovery
implementation. Specify IDs, ancestry, examples, exclusions, multi-branch rules,
decision reasons and policy versions. Add the Games/GTA and Nature/Koalas cases,
multilingual equivalents, ambiguous acronyms, mixed pages, rare topics and unrelated
near-neighbours. Reserve a new labelled holdout set before choosing parameters;
do not retune on the frozen earlier experiment or older closed cohorts.

Measure leaf precision, wrong top-level branches, candidate-route coverage,
ancestor fallback accuracy, useful assignment coverage and stability. Report
precision versus coverage and uncertainty rather than improving specificity by
forcing more matches. Proposed release targets are at least 98 percent precision
among accepted specific assignments and at most 1 percent wrong top-level branches,
with adequate independently labelled examples; do not claim these rates from a
handful of successes. Sparse topics and languages need separate reports.

Completion: deterministic reference classifier, adversarial tests and a frozen
evaluation protocol. Select no production threshold before this evidence exists.

### Phase 2 Build persistent taxonomy and background assignments

Design additive, least-privilege PostgreSQL migrations and the indexed worker queue.
Build prototypes from validated existing public embeddings without recapturing
pages. Support branch-local updates, stale-job rejection, replay-safe outcomes,
deletion propagation and explicit resource limits. Keep the current runtime on its
existing assignment policy during this phase.

Completion: synthetic/native database tests, concurrent worker/read tests,
resource benchmarks, schema review and independently reproducible shadow decisions.

### Phase 3 Connect hierarchy to discussion discovery

Serve semantic paths and parent feeds with current bounded cards. Preserve global
Search Topics and add breadcrumbs plus a clear specific-topic label to discussions.
Bind pagination to the selected semantic subtree and relevant public-thread state,
not every unrelated crawler revision. Refetch bodies rather than replay stale cards.
Ancestor aggregation must not duplicate roots or expand write/Insight authority.

Completion: actual disposable browser checks for empty/ambiguous pages, broad and
specific feeds, Next/Back, navigation, keyboard focus, pending drafts, account changes,
deletion, and a continuously running crawler. Do not declare page assignment replaced.

### Phase 4 Backfill page and thread bindings in shadow mode

Create a resumable, idempotent conversion over current Source embeddings and
existing public threads. Record old-to-new mappings and unresolved cases. Leave
all canonical assignments, receipt history, posts, reply ancestry, ownership,
timestamps and private/account stores unchanged. New writes during the backfill
must be included through scoped current-input checks, not overwritten by a snapshot.

Compare old/new behaviour read-only on representative pages. Review unexpected
merges, ambiguous branches and owner corrections. Never treat the old matcher as
ground truth; compare both against independent labels.

Completion: quality and latency gates pass; exact record-preservation checks and
a migration/cutover report identify every remaining unresolved case and limit.

### Phase 5 Activate semantic assignment and preserve original routing

Define the new canonical command/receipt boundary before activation. Existing
clients must remain compatible or fail with an explicit upgrade requirement, not
misinterpret a semantic node as an old Topic ID. New-root writes require the exact
current Source and accepted destination. Existing replies continue to address their
original root and canonical destination, even when read through a parent feed.
Global discovery and broad aggregation never substitute for Source/account/native
proofs or grant cross-Topic/foreign-thread writing.

After explicit owner approval of the concrete migration, recovery location and
retention, create the agreed encrypted backup, apply reviewed migrations, complete
the mapping and activate only checked code. Keep the crawler running where the
safe migration allows; coordinate any required interruption separately. Disable
the old exhaustive assignment path only when the new route and write proofs pass.

Completion: actual saved-page/new-page checks, unchanged historical message records,
working human writes and strictly guarded AI paths in offline fixtures, preserved
pairing/provider sign-in, advancing crawler/dashboard, and measured concurrency.
Any real AI test or account appointment still needs its own current authorization.

### Phase 6 Expose owner management after admin access is approved

Add the approved dashboard admin surface for labels, aliases, child approval,
branch presentation depth, examples, exclusions and reviewed corrections. Display
the impact before a save and preserve stable topic identities and historical thread
bindings. Do not silently turn popularity into an assignment threshold change.

Completion: unauthorized users cannot manage topics; explicit saves are revision
checked; branch edits, rollback and deletion preserve content and authority.

## Rollback and definition of done

Rollback switches semantic policy/index revisions or disables the new projection;
it never restores an old database over accepted writes or deletion. Once new
semantic destinations receive writes, use a compatible routing bridge/forward
repair, not an old binary or lossy remapping. Keep new accepted destinations
addressable during rollback.

The feature is complete when pages reach the deepest independently supported
topic, uncertain pages remain broad or page-only, parent feeds show existing child
discussions exactly once, owner branch control works through approved access, and
new-page classification no longer depends on the old catalog-wide assignment scan.
Removing empty canonical containers, inventing a universal taxonomy, or forcing
every page into an existing topic is not a completion criterion.
