# Synthetic-only normalized-state migration and recovery plan

Status: design for review, 2026-10-05. No owner database was opened, copied, or converted. This plan does not activate a schema, remove the current 100-Source/100-Topic limits, or authorize a backup/export. It follows ADR-016, ADR-023, and ADR-044. Implement and test against freshly constructed synthetic `demo-state/v1` and `/v2` rows in isolated temporary databases first; obtain a separate owner-data/security decision before a real cutover.

## Source contract and proposed shape

The current `demo_state` STRICT table has one row (`singleton=1`) with `schema`, `generation`, `revision`, and an at-most-8-MiB JSON `document`. Opening validates exact column shape and the JSON; a `/v1` row is automatically upgraded to `/v2` and increments `revision`. The new migration must accept only validated `/v2` input, or explicitly perform the already-reviewed `/v1` conversion once before normalizing. Unknown versions, extra SQLite objects, malformed rows, and failed validation stop closed. The service must be offline and hold the sole database writer; its present opener rejects extra tables, so a staged dual-schema database cannot be opened by the current binary.

Proposed schema version `normalized-state/v1` uses STRICT tables, `PRAGMA foreign_keys=ON`, and transaction-end checks for affected roots, links and identity constraints, with full projection validation at migration/recovery checkpoints. This is a relational representation of *existing* state, plus an initially empty candidate-edge table. It creates no second vector, text cache, semantic label, or new Source lineage. Use stable string IDs as primary keys and a small global ID registry (or equivalent cross-table assertion) to retain the current cross-kind collision rule. Do not recycle a deleted ID within a generation. The schema is a design target, not the existing prototype's schema.

Add indexes for `source_topic_links(topic_id, source_id)`, `discussions(topic_id)`, `contributions(discussion_id, created_at, ordinal, id)`, `contributions(root_id, ordinal, id)`, `contributions(origin_source_id)`, `root_anchors(source_id)`, and Source keyset order. Use restrictive FKs for provenance-bearing references: Forget first pins dependent roots and nulls every matching root/reply origin, then deletes link/vector/edges/Source in the **same transaction**. Do not use a cascading Source delete that silently erases or strands discussions.

## Synthetic migration and cutover protocol

1. In a socket-denied test process, construct synthetic JSON snapshots covering current `/v2`, exact `/v1` migration, legacy topic pins, source roots, reply origins, changed representation stamps, learned/fixture Sources, agent insights, withdrawn bodies, deleted Topics, and tied timestamps. Store only under a freshly created `topic-cloud-synthetic-*` OS temp directory. Never point a test at `apps/local-service/data/demo.sqlite`, another path, or a supplied owner file.
2. Stop synthetic writers; open the synthetic database exclusively and check SQLite integrity, expected `demo_state` table shape, singleton row, byte ceiling, exact JSON/schema/header match, and `assertValidPersistedState`. If `/v1`, run the existing `migrateLegacyState` logic in the same transaction and pin all old roots. Reject any orphan/collision or unexpected object. Record source row hash/counts only in process memory for verification; do not log URL, title, body, vector, token, or digest values.
3. `BEGIN IMMEDIATE`; create normalized tables in that transaction. Insert Topics, Sources/vectors, links, Discussions, roots then replies in verified parent-topological order, revisions, anchors, and metadata with prepared statements; reject cycles. Preserve the original contribution ordinal regardless of insertion order. Preserve every ID, string, boolean, null, stamp, and revision exactly. Edges remain empty. Run FK check, integrity check, full domain invariant validation, and a reverse projection comparison against the input. Compare canonical field values rather than raw JSON key order; also recompute original operation/source stamps against unchanged data.
4. Force failures after each table family, halfway through contributions, during link/anchor validation, and before commit; prove rollback leaves the original singleton readable byte-for-byte and no active normalized schema. A successful synthetic commit switches one explicit schema marker/reader dispatch atomically with the tables and, according to the selected recovery option, drops `demo_state` or retains it as a gated shadow. The new service binary must open only the matching active version; old binary must fail closed rather than initialize or rewrite. No request is served between conversion and validation.
5. Reopen with the new reader, project API views, count roots/replies/revisions, and run synthetic Forget, root/reply withdrawal, Source correction, Topic deletion, Clear, reset, and stale-version rejection. Test whole-subthread routing as one revision and confirm edge churn changes no post ID/destination. Keep malformed/future schema refusal tests. Separate trust/security and QA reviews precede any owner-data proposal.

For a *real* cutover, decide the recovery arrangement first and receive explicit approval. A single SQLite transaction protects pre-commit failure, but it cannot restore old application behavior after a committed faulty conversion. The present `DELETE` journal plus `FULL` sync gives atomic SQLite transactions; opening an owner DB to test or staging persistent duplicate owner content is outside this synthetic mandate. If approved, quiesce the service and browser writes, verify the exact path and database identity without printing content, require adequate free disk and, if backup/shadow is selected, a verified recovery destination, perform conversion offline with no provider/network, reopen and compare projected counts/IDs/hash summaries, then allow clients with a new API contract. On failure before commit, roll back and restart the old binary against the unchanged row. On failure after commit, stop writes and recover only by the *approved* method; never reconstruct missing origin or deleted bodies, and never auto-reset.

## Lifecycle and recovery choices requiring owner decision

The current prototype cannot simply be promoted: it requires `discussions.anchor_source_id` even though current Discussions are Topic-based; freezes `discussion_id` and `origin_source_id` although regrouping and Forget must change them; stores one current `body` rather than revisions/withdrawal; has no Topic/link, root anchor, `originalTopicId`, `learnedOrigin`, actor/insight, generation/revision, learned operation metadata or deletion lifecycle; and its `created_order` is not a captured timestamp. Its one candidate-edge table and indexed pagination are useful mechanics only. Its JSON-vector format has not been sized or benchmarked for current 384-dimensional E5 data.

Recovery alternatives to present with disk/retention costs: (A) owner-approved encrypted, access-restricted one-time local SQLite backup using SQLite's consistent backup API, with an explicit location, restore test, short expiry, and deletion procedure; (B) approved short-lived in-database old-row shadow retained until acceptance, then securely retired to the extent SQLite/OS permit; (C) no persistent duplicate, accepting that only pre-commit rollback exists and post-commit recovery depends on existing owner-managed backups. No option is implied by ADR-016's original **no backup/export** package. WAL/journal files, free pages, crash dumps, and OS backups can retain data after logical deletion; a retention promise cannot claim forensic erasure. Do not place a backup in git, temp test directories, cloud sync, or logs. Do not choose A or B or touch an owner row without the separate gate.

Forget: null all matching post origins, convert source-root anchors to their *current* Topic without changing `originalTopicId`/`learnedOrigin`, then remove Source/link/vector/edges. Withdrawal: purge every body revision, author, insight and origin; a withdrawn root pins its surviving reply tree to the current Topic. Topic deletion: resolve and disclose the exact current tree set, delete only approved trees and lineage with FK-safe ordering, then remove Topic/Discussion and affected Sources according to current command rules. Clear: delete all learned-origin trees even if moved into a manual/fixture Topic, keep unrelated manual/fixture posts, and remove learned Sources/Topics. In all cases maintain generation/revision CAS, atomic counts/views, no stale-draft retarget, and no resurrection from shadow rows or cached edges.

## Scale and verification gates

Keyset paginate Sources by `(source_ordinal, id)` and contributions by `(created_at, ordinal, id)` with a bounded page size and generation/revision-bound cursor; a stale cursor must restart or report conflict, not combine two state revisions. Define an API DTO that omits vectors and private bodies except authorized owner views. Keep the existing API/100-item limits until separately changed and tested; the database's larger capacity alone changes no product behavior. On >100, 1k, and larger synthetic catalogs measure p50/p95 Source page, Discussion page, neighbor lookup, write/Forget/regroup latency, disk bytes and WAL/journal behavior. Use bounded endpoint edge lists and incrementally refresh affected nodes; benchmark exact vector scan and candidate recall before selecting an approximate index. A graph edge is never a replacement for a primary Source-to-Topic posting anchor.

Acceptance evidence: exact round-trip of synthetic IDs/lineage/withdrawals, no leaked deleted body in active tables, atomic rollback at injected failures, old/new binary schema refusal, stale-version conflicts, invariant/FK/integrity checks, restart persistence, bounded query plans (`EXPLAIN QUERY PLAN`) and paginated API behavior. Record synthetic-only counts and timings. No real semantic-quality or large-scale claim follows from invented vectors.

Before owner-data migration, request explicit choices on: whether and where a temporary backup/shadow may exist and its retention/restore/deletion rules; whether migration may increment the visible revision; whether historical `/v1` is still in scope for real data; the acceptable service outage and rollback window; and the exact API/capacity change to accompany normalized storage. Obtain the separate owner-data/security approval and review the final implementation and recovery rehearsal before executing anything on retained owner state.
